Mic and Menu

Two changes to the /demo/<token> composer: Restart moves out of the message row and into a header menu, and an empty input offers a voice memo that comes back as a player with its transcription underneath. Everything below is clickable. Nothing has been built yet.

Recommended

Restart belongs in the header.

On a phone it is currently a full width button sitting under the composer, louder than Send on a page whose only job is to get one more message sent. It is also not really a button: it holds the scenario switch, the WhatsApp handoff and the quota. That is page chrome.

Recommended

Yes to voice memos, and it is cheap.

The engine already transcribes inbound audio and stores it as a player-ready attachment, because WhatsApp leads send voice notes constantly. The browser demo builds the exact payload shape that pipeline reads, with the media fields left empty. Fill them in and it works.

One thing that must not regress: when the demo finishes, the composer disappears and Restart is the only control left, which is correct. Move it to a header icon and that moment loses its call to action. So the recap gets its own Run it again button at the end, on both the desktop rail and the mobile card.

02 — The voice memo

Empty input, so the button is a mic

The mic sits in the send button's own slot and morphs into the send arrow the moment anything is typed, the way WhatsApp does, so there is nothing to learn and nothing shifts. Try it: type in the box, clear it again, then tap the mic and record for a few seconds.

What each state is doing

idle Mic, not SendThe input is empty, so there is nothing to send. One button, two jobs, no extra chrome in the row.
typing Morphs to SendSame position, same size, no layout shift. Clear the box and the mic comes back.
rec Tap to start, tap to sendNot hold-to-talk: that is awkward with a mouse and a first-time visitor will never find it. Trash on the left, 30 second cap, timer turns amber at 25.
sent Player first, transcript secondThe bubble appears instantly from the local recording. Whisper takes one to three seconds, so the transcript fades in under it.
why The transcript is the trustShowing what the AI heard turns a noisy-room mistranscription into "I mumbled" instead of "this thing is broken".

The commercial argument, not the design one: real leads in home improvement send voice notes because they are driving or standing on a roof. A prospect who rambles for fifteen seconds and watches a clean brief come out of it has seen the product. On a phone, speaking is also just easier than typing a convincing lead reply, so more visitors reach the recap, which is where the demo actually sells.

03 — What it costs

Most of the pipeline is already there

A browser voice memo walks the same path a WhatsApp one already does. Green is built and running today. Amber is the new work.

New Record in the page, POST as base64 JSON demo.html → /web-demo/<token>/voice
New, small Fill the media fields on the payload the demo already builds web_demo_routes.py:380
Built Audio branch: transcribe, prefix, attach, fallback line if it fails inbound_handler.py:190
Built Groq Whisper on bytes, base64 attachment out tools/voice_service.py:158
Built Lands in the CRM inbox as a voice note, player and transcript already rendering ChatBubble.tsx:169
01 The proxy cannot carry multipart server/routes/demo.ts:456 re-serialises every POST as JSON and only allows four suffixes. That allowlist is a security property, not an oversight, so the audio goes up as base64 inside JSON instead. Needs a 2mb body limit on that one route: the Express default of 100kb is already too small for a 30 second memo.
02 Never put the audio in the polled state The page re-fetches the whole conversation every 1.6 to 6 seconds. Two base64 memos would make every poll about a megabyte. The state carries an id, the page fetches the audio once, on play, and only if it is not already holding the blob it just recorded.
03 render() rebuilds the entire page An <audio> element inside a bubble dies on every poll, mid-sentence. One singleton player lives on body and the bubbles just paint its state, which is how the CRM's own player manages playback across a list.
04 Chrome records webm, Safari records mp4 audio/webm;codecs=opus misses the extension map today and silently falls back to .ogg. Both copies of that map need webm, and the content type needs normalising first. Worth verifying Groq accepts webm before building, because a transcode step on the Pi would change the maths.

The four calls, made

02 The menu reaches Gabriel himselfWhatsApp on +31 6 84446349 or gabriel@leadawaker.com, both prefilled with which demo the visitor is looking at, ruled off from the demo's own controls so the two WhatsApp links cannot be confused. Deliberately not a booking page, and not the campaign's booking chain, which points at the calendar the demo is simulating.
03 30 second capTimer turns amber at 25, hard stop at 30. Keeps answers punchy and every upload under 80KB.
04 The mic lives in the send button's slotExactly one round button in the composer: a mic while the box is empty, the send arrow the moment anything is typed. Not advertised in the placeholder, because a mic in that position needs no explaining. A hint is a one line change later if usage says otherwise.

Not proposed here: the AI replying with voice. The stack has TTS and it would demo well, but it adds latency, cost and a per-language voice matrix to a page whose whole promise is speed. Separate decision.
